# AGENTS.md — terraform-renderer-generic

Diagnostic guide for AI agents and engineers debugging this module or a setup that
consumes it. Hand-maintained; keep the symptom table honest and evidence-based.

## What this repo is

A code generator, not infrastructure. It turns YAML workspace definitions into
plain Terraform files (`main.tf`, `versions.tf`, `providers.tf`, `outputs.tf`) that
a driver then executes.

- **root module** — renders exactly **one** setup from a `module_config` object.
- **`modules/infra-yaml-loader`** — discovers and merges the YAML for a **whole
  repository** and returns the workspace map. Drivers call this first, then call
  the root module once per workspace.

Consumers: `dasmeta/cloud/tfe`, `dasmeta/cli/terragrunt`, `dasmeta/cli/terramate`.
End users never call this repo directly; they edit YAML in an infrastructure repo
(`payconomy/infrastructure`, `sela-ai/infrastructure`, …) whose `_metacloud.tf` is
generated by Meta CLI.

```
infra repo YAML ──▶ infra-yaml-loader ──▶ driver ──▶ renderer (per workspace) ──▶ *.tf ──▶ terraform
                    (discovery+merge)     (ordering,     (templating)
                                           backend)
```

**When something is wrong, first decide which stage owns it.** Missing workspace or
wrong merge → loader. Wrong ordering/linking → loader + driver. Wrong file content →
renderer templates. Wrong plan → the target module itself, not this repo.

## Repo map

| path | what it owns |
|---|---|
| `locals.tf` | renderer logic: provider blocks, linked-setup mapping, interpolation replacement |
| `templates/*.tftpl` | the actual generated file contents |
| `variables.tf` | renderer input contract (`module_config`, `terraform`, `linked`, `provider_configs`) |
| `modules/infra-yaml-loader/locals.tf` | discovery, shared-config merge, filtering, link detection |
| `examples/basic`, `modules/infra-yaml-loader/examples/basic` | executable tests (`check` blocks) — CI runs these, there are no `.tftest.hcl` files |
| `specs/NNN-*/` | spec/plan/tasks per change |

## The YAML contract

Enforced in `modules/infra-yaml-loader/locals.tf`:

- **Workspace key** = file path relative to `yamldir`, minus `.yaml`.
  `2-products/demo/dev/app.yaml` → `2-products/demo/dev/app`.
- **A file becomes a workspace only if** it resolves to both `source` and
  `version`. Local sources (`./`, `/`, `~`) get `version = "local"` automatically.
  Everything else is silently dropped — see `yaml_files_raw` vs `yaml_files`.
- **Excluded from discovery**: `_.yaml` / `*/_.yaml` (shared config), `metacloud.yaml`,
  anything under `_terragrunt/` or `_terraform/` (generated output), anything under
  `.terraform`.
- **Shared config merge is textual**: root `_.yaml`, matching folder `_.yaml`s, and
  the workspace file are concatenated and then `yamldecode`d **once**.

## Linked workspaces

There are exactly two ways to declare a dependency, and both name the workspace
explicitly. **Nothing is inferred from directory names** — a rule that guessed links
from `2-products/.../setups/` path shape was removed in 1.2.2, see
`specs/006-infra-yaml-loader-path-linking/`.

```yaml
# 1. explicit — ordering, or a dependency with no value reference
linked_workspaces:
  - 0-accounts/root/iam-prod
  - 1-environments/prod/rds-postgres

# 2. a reference — the path inside ${...} *is* the link
providers:
  - name: kubernetes
    variables:
      host: ${1-environments/dev-2/eks.cluster_host}
```

Form 2 is detected twice, independently: by the loader across `variables` and
`providers` (drivers use it for ordering) and by the renderer per workspace (used to
generate the `data` blocks and rewrite the reference). `terraform-tfe-cloud` uses
only the renderer's detection plus the explicit list — it does not read the loader's
`auto_detected_linked_workspaces` at all.

## Diagnostics: symptom → cause → check

| symptom | likely cause | check / fix |
|---|---|---|
| `Invalid template interpolation value … string required, but have tuple` in `modules/infra-yaml-loader/locals.tf` | loader ≤ 1.2.1 with a workspace path matching the old `2-products/<x>/<y>/setups/<z>` rule | upgrade loader to ≥ 1.2.2. Not fixable by renaming folders. |
| `Call to function "coalesce" failed: no non-null, non-empty-string arguments` | loader < 1.2.1 with an empty or incomplete YAML file | upgrade loader; see `specs/005-*` |
| module fails while **parsing** on HCP, before any plan output | Terraform < 1.8 with `provider::deepmerge::mergo` — provider-defined functions need 1.8+ | check the *workspace's* Terraform version in HCP, not your local CLI. Renderer ≥ this release declares `~> 1.8`, so you get a version error instead of a parse error. |
| a workspace silently missing from generated output | its YAML has no `source`, or no `version` for a non-local source | compare `yaml_files_raw` (pre-filter) with `yaml_files` — the key will be in the first and absent from the second |
| driver depends on a workspace that does not exist (`region`, `bucket_name`, `param1`) | a **literal** `${...}` in `variables`/`providers` is read as a workspace reference — there is no existence filter | search the YAML for `${` values that are not workspace paths; move them out of scanned fields or make them real references |
| values from a folder `_.yaml` missing from the workspace | top-level keys do **not** deep-merge (see traps) | dump the merged doc via `yaml_files_raw`, then switch to anchors/aliases |
| link declared but no `data` block generated | reference points at a path that is not a workspace key | check the exact key exists in `yaml_paths` (path minus `.yaml`, no leading `./`) |
| edits to generated `.tf` disappear | `_terraform/` and `_terragrunt/` are outputs, regenerated every apply | change the YAML or the templates, never the generated files |

## Inspecting a real setup

The fastest way to see what the loader makes of a customer repo — no driver, no
credentials, no state:

```hcl
# /tmp/loader-probe/main.tf
module "l" {
  source  = "dasmeta/generic/renderer//modules/infra-yaml-loader"
  version = "1.2.2"                       # or source = "/path/to/local/checkout/modules/infra-yaml-loader"
  yamldir = "/path/to/customer/infrastructure"
}
output "paths" { value = module.l.yaml_paths }
output "links" { value = module.l.auto_detected_linked_workspaces }
output "raw"   { value = module.l.yaml_files_raw }
```

```bash
terraform init -backend=false && terraform plan          # reproduces loader-stage errors alone
echo 'module.l.yaml_files["2-products/demo/dev/app"]' | terraform console   # one merged workspace
echo 'module.l.auto_detected_linked_workspaces' | terraform console         # every detected link
```

Comparing `yaml_files_raw` against `yaml_files` answers "why is my workspace not
generated?" in one step. `.terraform` directories are excluded, so pointing the probe
at a working repo is safe.

To validate a module change in this repo, run the examples — they are the test suite:

```bash
terraform -chdir=modules/infra-yaml-loader/examples/basic init -backend=false
terraform -chdir=modules/infra-yaml-loader/examples/basic plan   # check-block failures appear as warnings
```

A `check` failure prints as a **Warning**, not an error. Grep for `Warning` — a plan
that "succeeded" can still have failing assertions.

## Known traps

- **Shared `_.yaml` does not deep-merge.** The files are concatenated and decoded
  once, so a duplicate top-level key wins outright. If `_.yaml` sets
  `variables: {a: 1}` and the workspace sets `variables: {b: 2}`, the result is
  `{b: 2}` — `a` is gone. Verified against the loader example. The intended mechanism
  is YAML **anchors and aliases**, which work because the merge is textual:

  ```yaml
  # _.yaml
  provider_aws_dev: &provider_aws_dev
    name: aws
    variables: {region: eu-central-1}
  # workspace.yaml
  providers:
    - <<: *provider_aws_dev
  ```

- **Folder shared config matches by substring, not prefix.** The key is the folder
  path with a trailing slash, tested with `strcontains`. A `_.yaml` in `a/b/` also
  applies to `x/a/b/c.yaml`.
- **Root module and submodule are versioned together but pinned separately.**
  Consumers currently pin `dasmeta/generic/renderer` at one version and
  `dasmeta/generic/renderer//modules/infra-yaml-loader` at another, so two copies of
  this repo at two tags are downloaded. Check both pins before concluding a fix "did
  not land".
- **A generated stack's `required_version` is not this repo's.** It comes from the
  `terraform.version` input (default `~> 1.3`), which is deliberately independent of
  the constraint this module itself needs.
- **Unused module outputs are still evaluated.** A defect in a code path a driver
  never reads can still break its plan — that is exactly how the 1.2.1 path-linking
  bug broke `terraform-tfe-cloud`.

## Version compatibility

| component | constraint | why |
|---|---|---|
| root module | `~> 1.8` | calls `provider::deepmerge::mergo`; provider-defined functions need Terraform 1.8+ |
| `modules/infra-yaml-loader` | `~> 1.3` | pure HCL, no provider functions — keep it low so drivers stay flexible |
| generated stacks | `terraform.version` input, default `~> 1.3` | consumer policy, not a module requirement |

## Changing this repo

- Write a `specs/NNN-name/{spec,plan,tasks}.md` package before changing behavior.
- Add or extend an example with `check` blocks — that is the only test mechanism here.
- `pre-commit` runs on commit and rewrites README tables via `terraform_docs`; stage
  its changes and re-commit rather than hand-editing generated tables.
- Conventional commits drive semantic-release: `fix` → patch, `feat` → minor. A new
  input variable is a `feat`, so prefer removing dead behavior over parameterizing it.
- Both README requirement tables and the module code must agree on version
  constraints; CI does not check that for you.
